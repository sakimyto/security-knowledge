# 事故DBの週次更新手順

この公開DBの保守と、利用者の環境を点検する週次運用は別の作業です。DBの保守では、新しい事故報告と既存事例の追記を確認します。利用者の環境は、DBに更新がなくても点検します。

収集の入口には、[piyolog](https://piyolog.hatenadiary.jp/)、[JPCERT/CC](https://www.jpcert.or.jp/)、[CISAの悪用済み脆弱性一覧](https://www.cisa.gov/known-exploited-vulnerabilities-catalog)などを使います。企業・開発元・調査機関の一次情報へ戻り、事故の発生、公表、原因の説明、AIの関与を別々に確認します。脆弱性の公表だけで、実際の事故が起きたとは判断しません。

保守者は、最終成功日時、確認したURLと更新日、候補の状態を非公開の状態ファイルへ保存します。重複キーは正規化したURLと公表日です。既存事例の追記は、事例IDと出典URLに対応させます。失敗した取得を「更新なし」と記録しません。

一回の収集は直近7日を基本とし、前回の成功日から空白があればその期間を明記します。入口ごとの件数と追加調査の上限を決めます。新しい候補、保存済みの再確認対象、検証済み未公開の差分がすべて0件なら終了します。国内・海外の候補を確認し、原因が未公表なら `unknown` を保ちます。転載はせず、短い要約と出典、主張ごとの根拠を作ります。

候補を編集したら、参照整合性、Schema、テスト、配布データとの一致を確認します。公開前に差分と根拠をレビューし、確認した対象だけの `reviewedAt` を更新します。確認していない全事例の日付を一括更新しません。公開した版とGitコミットを状態ファイルへ残します。

一次資料が取得できない候補は、理由と再確認の印を `intake/` に残します。404やTLS失敗、本文のないページ、別の事故の資料を確認済みにしません。元の入力値は未検証として保存し、件数の訂正や初報日不明を隠しません。

## 承認済みの自動公開

このDBの保守者は2026-10-09に公開の自動化を承認しました。確認済みの差分をPRにし、Schema、参照、日付、全Nodeテスト、報告JSON、配布データの再生成一致を確認します。必須CIが成功したPRをmergeし、同じコミットから版を付けたReleaseと配布ファイルを公開します。閲覧サイトを運営している場合は、そのミラーと配布データを同じ版へ同期し、サイト側の必須検証とCIを通してdeployします。匿名で取得した公開版のバージョン・ハッシュを照合して完了とします。

無関係な作業中の変更がある場合は、最新のmainから一時チェックアウトを作ります。必須チェックを迂回せず、確認対象の差分だけを公開します。未マージのbranchは削除しません。

取得失敗は更新なしとして保存せず、以前の成功状態を維持します。出典の矛盾、公開範囲、権限不足など自動判断できない問題は該当差分の公開を止め、具体的な問題を報告します。処理済み候補の理由、公開コミット、再確認対象、通知済み状態を保存し、同じ結果を繰り返し通知しません。変化がないときは静かに終了し、公開完了、失敗、重要な訂正、利用者の判断が必要な場合だけ通知します。
