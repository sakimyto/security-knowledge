# 事故DBの週次更新手順

この公開DBの保守と、利用者の環境を点検する週次運用は別の作業です。DBの保守では、新しい事故報告と既存事例の追記を確認します。利用者の環境は、DBに更新がなくても点検します。

収集の入口には、[piyolog](https://piyolog.hatenadiary.jp/)、[JPCERT/CC](https://www.jpcert.or.jp/)、[CISAの悪用済み脆弱性一覧](https://www.cisa.gov/known-exploited-vulnerabilities-catalog)などを使います。企業・開発元・調査機関の一次情報へ戻り、事故の発生、公表、原因の説明、AIの関与を別々に確認します。脆弱性の公表だけで、実際の事故が起きたとは判断しません。

保守者は、最終成功日時、確認したURLと更新日、候補の状態を非公開の状態ファイルへ保存します。重複キーは正規化したURLと公表日です。既存事例の追記は、事例IDと出典URLに対応させます。失敗した取得を「更新なし」と記録しません。

一回の収集は直近7日を基本とし、前回の成功日から空白があればその期間を明記します。入口ごとの件数と追加調査の上限を決め、新しい候補がなければ終了します。国内・海外の候補を確認し、原因が未公表なら `unknown` を保ちます。転載はせず、短い要約と出典、主張ごとの根拠を作ります。

候補を編集したら、参照整合性、Schema、テスト、配布データとの一致を確認します。公開前に差分と根拠をレビューし、確認した対象だけの `reviewedAt` を更新します。確認していない全事例の日付を一括更新しません。公開した版とGitコミットを状態ファイルへ残します。

取得失敗、出典の矛盾、権利や公開範囲の不明点があれば、以前の成功状態を維持して判断を求めます。通知は新しい候補、修正案の完成、失敗、利用者の判断が必要な場合に限ります。定期実行のサービスと公開権限は、保守者が自分の環境で設定します。
