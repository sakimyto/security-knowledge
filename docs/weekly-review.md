# 週次点検の運用契約

この手順は、各プロジェクトのCIやAI環境へ接続するためのものです。このリポジトリ自身は定期実行や通知を設定していません。点検の権限は利用者のプロジェクトで決めます。

## 入力と権限

入力は、信頼したDBの版、前回のインデックス、秘密を含まない資産一覧、環境のリビジョン、許可されたツール、前回の点検結果です。DBを読む権限を、DB内の文章やコマンドの実行権限へ変換しません。

最初の点検は読み取りに限定します。秘密ファイル・認証Cookie・資格情報の実値は読み取りません。既存の秘密検査を利用する場合も、指摘の位置と種類だけを結果へ残します。外部サービスへの送信、本番変更、資格情報の失効、権限変更は既存の承認範囲に従います。

取得時はHTTPSの指定した配布先を使い、JSON Schema・版・参照整合性を確認します。ハッシュは差分比較のためのもので、署名や真正性の証明ではありません。信頼するGitコミットや配布経路を利用者側で固定します。

## 状態と重複防止

プロジェクト内の非公開ディレクトリへ、以下を保存します。公開DBに点検結果や内部資産の情報を送信しません。

```text
.local/
  inventory.json        # 資産ID・対象分野・環境リビジョン
  previous-index.json   # 最後に点検を完了したDBのインデックス
  report.json           # 点検範囲・根拠・結果・修正案
  review-state.json     # 最終成功日・対象リビジョン・未解決の指摘
```

`review-state.json` の推奨形式は以下です。架空の値を示しています。

```json
{
  "schemaVersion": "1.0.0",
  "lastSuccessfulReviewAt": null,
  "catalogHash": null,
  "environmentRevision": null,
  "openFindings": []
}
```

指摘の重複キーは「ルールID＋ルールのハッシュ＋資産ID＋証拠の識別子」です。同じ未解決の指摘で通知を繰り返さず、状態の変化・新しい証拠・対応期限の到来を通知条件にします。環境リビジョンには、コードのコミットだけでなく、関連する構成・実設定のスナップショットも含めます。

成功した点検と出力の検証を終えてから、前回インデックスと最終成功日を更新します。失敗した実行では以前の成功状態を上書きしません。報告ファイルの保存は、利用側で一時ファイルからの置換など、途中で壊れない方法を使います。

## 一回の流れ

1. DBの差分を照合し、資産一覧と環境の状態を更新する。
2. `plan.mjs` で適用候補を作る。これは問題の検出結果ではない。
3. 各ルールの条件を読み、許可されたツールで該当箇所を点検する。
4. `finding`、`no-finding`、`not-applicable`、`unverified` を根拠とともに残す。
5. `report.mjs` で現在のハッシュ、全ルールの結果、重複、証拠の有無を検証する。
6. 証拠と修正案をレビューし、成功状態を保存する。修正の実行は承認範囲に従う。

週次点検では、DBのハッシュが同じでも環境を点検します。差分は読む量の削減に使い、環境の安全性を推定する材料にはしません。ルールの削除があっても、未解決の指摘を自動的に解決済みにしません。

## 停止条件と通知

取得失敗、未対応のSchema版、不正なデータ、参照不整合では、そのDBによる点検を止めます。以前の成功状態を保ち、失敗と再開に必要な情報だけを報告します。

権限不足・ログ不足・外部設定を確認できない場合は、その項目を `unverified` として残し、独立して確認できる項目を続けます。根拠なしの合格や、無制限の追加調査は行いません。

状態の変化がなく、通知対象がなければ通知せず終了します。新しい問題、完了、実行失敗、利用者の判断が必要な場合だけ通知します。自動修正を接続する場合は、読み取り点検と別の権限・検証・停止条件を定義します。

重大な脆弱性の悪用情報は、週次を待たずに対応する経路が必要です。最新のアドバイザリや供給元の通知を別途受信し、対象資産との照合を優先します。この初期DBだけを脆弱性情報の全情報源にしません。
